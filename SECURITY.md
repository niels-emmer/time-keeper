- `GET /api/summary/monthly` — read-only monthly analytics payload for the Monthly tab (goals, pace, projections, billable split)
- `POST /api/entries` — create a completed manual/backfilled time entry from the day log UI
- `PATCH /api/entries/:id` now validates any reassigned `categoryId` against the caller's own categories and rejects invalid time ranges (`endTime <= startTime`)
- All of the above endpoints require Authentik auth and scope writes/reads to `req.userId`
- The monthly summary endpoint is read-only and derives all data from rows already scoped to `req.userId`
- The manual-entry endpoint validates category ownership and requires a completed time range, so it cannot be used to forge a second running timer

## What has not been done

- The legacy `monthly_project_goals` table is retained for migration/backward-compatibility, but no automated cleanup/removal migration has been added yet

## Authentication

The application supports two auth paths.

### Trust model (C-1)

Nothing in this stack is published to the host. Both containers attach only to the external `proxy-net` Docker network; Nginx Proxy Manager (also attached to that network) reaches `frontend:80` and `backend:3001` by Docker service name. There is no host-port binding and no LAN exposure.

The `X-authentik-email` header is trusted only when all of the following hold:

1. **Trusted peer.** The TCP peer address (`req.socket.remoteAddress`, never the client-controlled `X-Forwarded-For`) is loopback, a private range (RFC 1918, IPv6 ULA/link-local), or inside the optional `TRUSTED_PROXY_CIDRS` allowlist. A public peer presenting the header is rejected with 401.
2. **Internal token.** In production the request also carries `X-Internal-Token` equal to `INTERNAL_PROXY_SECRET`. nginx injects it server-side and overwrites any client-supplied value, so an outside caller cannot supply their own.
3. **Same origin** for non-GET header-authenticated requests (see the CSRF row below).

**Nginx must never be the only hop.** It forwards whatever `X-authentik-email` arrives and stamps the token on top, so publishing `frontend:80` would let anyone who can reach it authenticate as any email they choose. The peer allowlist is defence in depth; it is not permission to publish the port.

### Path 1 — Browser / PWA (Authentik forward auth)

```
Internet → NPM (TLS + Authentik forward auth; proxy-net) → frontend nginx:80 → backend:3001
```

The backend reads the `X-authentik-email` header set by the Authentik outpost. Under the trust model above, a header from a non-private peer is ignored (401), and in production the request must also carry a matching `X-Internal-Token` derived from `INTERNAL_PROXY_SECRET`; if the secret is missing or mismatched the backend returns 401. Header-authenticated non-GET requests are also checked for a same-origin `Origin` or `Referer` before they reach mutating routes.

See [docs/integration/auth.md](docs/integration/auth.md).

### Path 2 — Native app (Bearer token via api.* subdomain)

```
Internet → NPM (TLS only, no forward auth; proxy-net) → backend:3001 → Bearer token check
```

Added to support the macOS status bar app. The `api.*` subdomain bypasses Authentik but the backend validates the `Authorization: Bearer <token>` header itself:

- Tokens are 32 random bytes encoded as base64url (256-bit entropy)
- Only the SHA-256 hash is stored in the database — a DB breach does not expose usable tokens
- Tokens are shown once on creation and cannot be retrieved again
- Tokens are revocable from the web app (Settings → Personal Access Tokens)
- Tokens expire one year after creation; expired tokens are rejected server-side
- Token management endpoints require Authentik-header auth — a Bearer token cannot create or list tokens
- The backend publishes no host port; NPM reaches `backend:3001` over `proxy-net`
- The Bearer path is unaffected by the peer allowlist — a valid token is accepted from any peer
- HTTPS is enforced by NPM on the api.* subdomain

See [docs/integration/api-subdomain.md](docs/integration/api-subdomain.md).

## Data storage

- All data lives in a **single SQLite file** on the host (`/data/time-keeper.db` inside the backend container, mounted as a Docker volume).
- There is no external database, no cloud sync, no analytics, no telemetry.
- The file is readable by anyone with shell access to the host. Protect it with standard filesystem permissions and volume encryption if required.
- The backend container now drops to the non-root `node` user at runtime; SQLite still remains host-readable to anyone with host access.
- WAL mode is enabled, so recent commits live in `time-keeper.db-wal` until checkpointed. **Backup must take a consistent snapshot** (online `better-sqlite3` backup, or stop the backend first) — copying only `time-keeper.db` while the backend runs can silently lose the newest entries (finding M-5). Procedure and restore drill: [docs/operations/runbooks.md](docs/operations/runbooks.md#rb-006-wal-safe-backup).
- Timestamps stay UTC (invariant I-004). `user_settings.timezone` stores only the IANA zone used to bucket entries into local days; it contains no location history or telemetry.

## Container privileges

The two containers do **not** share the same privilege model, and the difference is intentional (finding L-12):

- **Frontend nginx runs its master process as root.** It starts from the official `nginx:alpine` image and binds privileged port 80, which requires root; nginx then drops its worker processes to the unprivileged `nginx` user. nginx only serves the pre-built static bundle and reverse-proxies `/api/`, so it executes no user-supplied code and never writes to the data volume. Combined with the fact that the container publishes no host port (see the trust model above), running the stock image as root on `:80` is acceptable here. A non-root image on an unprivileged port is possible but not required for this deployment.
- **Backend runs as the non-root `node` user**, as described under Data storage above.

## Dependency audit

Audited with `yarn npm audit --all --recursive --severity high` on **2026-11-14**. The audit is **not** clean: pre-existing high/critical advisories remain in transitive dependencies (a mix of runtime, build-time, and dev-only packages). Triage is tracked in the remediation plan's Phase 4; until then the CI `audit` job runs the command above and fails on findings rather than hiding them behind `continue-on-error`.

The frontend dependency graph was also refreshed on 2026-05-13: app/runtime deps now include `@tanstack/react-query` 5.100.x and `react-router-dom` 7.15.x, the frontend build/test toolchain was refreshed (`vite` 6.4.2, `vite-plugin-pwa` 1.3.0, `vitest` 4.1.6), backend tooling now uses `drizzle-kit` 0.31.10, and the root `resolutions` pin patched transitive versions for packages such as `@babel/plugin-transform-modules-systemjs`, `esbuild`, `fast-uri`, `ip-address`, `postcss`, `rollup`, and `serialize-javascript`.

`vitest`, `jsdom`, `vite-plugin-pwa`, `postcss`, and `tailwindcss` are build/test-only dependencies (not shipped in the production Docker image). They are omitted from the runtime table below.

`recharts` and `react-is` were added for the Monthly overview charts. `@testing-library/react` and `@testing-library/dom` were added as **dev-only** dependencies for frontend component and hook tests. `supertest` and `@types/supertest` are **dev-only** dependencies for the backend HTTP harness — they are not part of the production image.

Runtime dependencies and their risk profiles:

| Package | Version pinned to | Notes |
|---------|------------------|-------|
| `express` | `^4` | 15+ years old, very widely used, actively maintained |
| `better-sqlite3` | `^13` | Widely used SQLite binding; includes a native C++ addon. 13.x ships prebuilt binaries for current Node versions (including Node 26) and falls back to compiling with node-gyp — highest-risk category by nature of native code |
| `drizzle-orm` | `^0.45` | Newer library (2022–); less battle-tested than Prisma but growing adoption. Upgraded from 0.38 to fix CVE-2026-39356 (SQL injection via identifier escaping). |
| `zod` | `^4` | Pure TypeScript; used for all input validation on the backend |
| `express-rate-limit` | `^7` | Simple, auditable rate-limiting middleware |
| `react` + `vite` | current | Mainstream, heavily used |
| `@tanstack/react-query` | current | Mainstream, well-maintained |
| `recharts` | current | Mainstream charting library used for the Monthly overview visualisations |
| `react-is` | current | Supporting dependency required by `recharts`; small surface area |
| `@radix-ui/*` / `shadcn/ui` | current | Accessible, widely used UI primitives |
| `@dnd-kit/*` | current | Pure JS drag-and-drop; no native code |

**To re-run the audit yourself:**
```bash
yarn npm audit
```

**The native addon caveat:** `better-sqlite3` ships prebuilt binaries for supported Node versions and falls back to compiling C++ at `yarn install` time using `node-gyp`. This is normal and the package is widely used, but it means you are trusting both the npm registry and, on a fallback, your local C++ toolchain. If this concerns you, inspect `node_modules/better-sqlite3/build/` after install.

## What has not been done

To be explicit about what a proper security review would include and this project has not had:

- No penetration test
- No static analysis (SAST) beyond TypeScript's type checker
- No dependency licence audit
- No end-to-end review of the deployed nginx / NPM configuration beyond the checked-in templates and compose wiring
- No assessment of the Authentik configuration for misconfigurations
- No fuzzing of API inputs beyond Zod schema validation
- No formal review of the new CSP against every self-hosted customization or browser extension scenario
